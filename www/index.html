Project Koios

The personal technical website of Eugene Joseph M. Ragasa.

It collects work in physics, teaching, computation, mathematical modeling, software, finance-oriented analysis, hardware, and other technical projects.

The topics vary. The method does not.

Index

The site is organized as a working archive. These are navigation labels, not marketing categories.

Notes Working notes, derivations, explanations, and references. Courses Course material for physics, materials science, computation, and modeling. Research Research sketches, models, simulations, and open problems. Software Code, notebooks, documentation, and computational tools. Finance and Modeling Finance treated as modeling and decision analysis, not stock tips. Devlog Build logs, decisions, dead ends, and work in progress.

Why this site exists

My main priority is not monetization or entertainment. I do not like marketing language, positioning language, or propaganda dressed up as communication strategy. This site is not a funnel, a product page, a course catalog, or a research-group brochure.

The point is to educate, share, and keep working in public while I do my job as a professor, improve my own skills, and tinker with things I want to understand better.

If I eventually monetize some of this work, I am not changing the basic deal. The site is not becoming bait. The work stays the work.

The problem

One problem with science education is that technology has moved faster than the textbooks, courses, and institutional structures that are supposed to support technical work.

At the same time, much of online technical content is optimized for attention, monetization, and audience growth. Much less of it is built around the harder question: can someone actually use this to do work?

Worse, a lot of material reduces technical education to software operation. It teaches people which buttons to press or which library function to call, but not what the model means, what assumptions it makes, where it fails, or how to rebuild the method when the tool is not available.

That is not understanding. That is dependency with better branding.

The standard

Project Koios is built around a simple standard: do not stop at words.

If an idea matters, define it. If it can be modeled, model it. If it can be computed, compute it. If it makes assumptions, state them. If it breaks, say where it breaks.

  1. Start with a real question.
  2. Identify the assumptions.
  3. Build the model.
  4. Connect it to traditional theory.
  5. Implement enough of it to see what it actually does.
  6. Explain the result without pretending the tool did the thinking.

The point is not to make technical work look easy. The point is to make it possible to follow, inspect, reproduce, criticize, and use.
